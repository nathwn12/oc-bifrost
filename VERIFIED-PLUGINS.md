# Verified plugins

Plugins smoke-tested against `oc-bifrost` on OpenCode V2. "Verified" means a run was performed — not an assumption.

There are **two mounting routes**, and a row says which one it exercised:

- **V1 hook translation** — a V1 factory/module; its hooks are bridged per the compatibility matrix.
- **V2 pass-through** — an `export default` `{ id, setup | effect }`; it is mounted as-is with the host context. A **dual-export** file (V1 named export + V2 default) takes this route for its V2 default; the V1 named export is left untouched.

Add yours with a PR: copy a row, state the plugin version, which route it exercised, the hooks it registers, and the command you ran to prove it.

**A plugin's external prerequisites are not the bridge's job.** RTK shells out to a `rtk` binary; without it on `PATH` the plugin disables itself — correctly, and quietly. A by-source `github:` fetch carries **no npm dependencies** — a plugin whose entry imports a package (personality's `@opencode-ai/plugin`, ignore's `ignore`, snippets' `@opencode/plugin` + friends) fails loudly at import until the package exists beside the fetched tree. Two flights proved the line precisely: personality and snippets loaded and ran the moment their one (respectively declared) dependency was provided in the sandbox — nothing in the bridge itself changed. When you add a row, say whether a binary, daemon, or credential had to exist first, so the next reader isn't debugging a plugin that is simply unmet.
